# 2026-11-07 — The web's start: mipmaps without powf

## User request

After v0.0.21 (the content apart from the .wasm), the web version was still
very slow, on an M4 Pro with 48 GB; the user suspects the loading of the
resources.

## Diagnosis

Measured on motorust.germade.dev (the game's v0.0.19) in headless Chromium:
the download is quick (the .wasm 14.7 MB brotli, content.pack 55 MB, ~3 s)
and the .wasm compiles in 0.36 s, but ~17.5 s pass in the game's `main`
before Bevy opens its window (the plugins' `build`, all on one thread), and
some 8 s more before the first frame is shown. A CPU profile (a build
keeping its function names) put **10 s in
`world::textures::generate_mipmaps`, 8.3 s of them in `powf`**: `to_srgb`
turned every channel of every texel of every mip level back into sRGB
through `Color::to_srgba`.

## Implementation (`src/world/textures.rs`)

- `to_8_bits`: the 255 linear values where one 8-bit code gives way to the
  next, worked out once, and a binary search among them, in place of the
  curve's `powf` per texel (the same rounding, but for a hair's breadth on
  a boundary).
- `SRGB_TO_LINEAR` / `UNORM_TO_LINEAR`: the 256 codes in linear space,
  worked out once, shared by `generate_mipmaps` and `average_color` (which
  also took `powf` for every pixel of the ground's textures).
- Test `a_linear_value_comes_back_to_the_8_bits_the_curve_gives`.

## Verification

- `cargo test`: 663 passed, 2 ignored. `cargo clippy --all-targets -- -D
  warnings` and `cargo fmt --all --check` pass.
- Profile of the game's web build with the mipmaps' change: until the
  window, 25.1 s → 17.5 s on this container's CPU; `generate_mipmaps`
  10.1 s → 3.3 s.

## Still at the start (measured after the change)

`WorldTextures` 4.3 s (decoding, enhancing and the mipmaps of every ground
texture), `spawn_sky` 2.7 s, the bikes' models 2.7 s and the props' packs
2.5 s: every theme's props and every bike's textures are made as the game
starts, whichever circuit is to be shown first.
