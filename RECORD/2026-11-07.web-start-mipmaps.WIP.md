# 2026-11-07 — The web's start: mipmaps without powf

## User request

After v0.0.21 (the content apart from the .wasm), the web version was still
very slow, on an M4 Pro with 48 GB; the user suspects the loading of the
resources.

## Diagnosis

Measured on motorust.germade.dev (the game's v0.0.19) in headless Chromium:
the download is quick (the .wasm 14.7 MB brotli, content.pack 55 MB, ~3 s)
and the .wasm compiles in 0.36 s, but ~17.5 s pass in the game's `main`
before Bevy opens its window (the plugins' `build`, all on one thread), and
some 8 s more before the first frame is shown. A CPU profile (a build
keeping its function names) put **10 s in
`world::textures::generate_mipmaps`, 8.3 s of them in `powf`**: `to_srgb`
turned every channel of every texel of every mip level back into sRGB
through `Color::to_srgba`.

## Implementation (`src/world/textures.rs`)

- `to_8_bits`: the 255 linear values where one 8-bit code gives way to the
  next, worked out once, and a binary search among them, in place of the
  curve's `powf` per texel (the same rounding, but for a hair's breadth on
  a boundary).
- `SRGB_TO_LINEAR` / `UNORM_TO_LINEAR`: the 256 codes in linear space,
  worked out once, shared by `generate_mipmaps` and `average_color` (which
  also took `powf` for every pixel of the ground's textures).
- Test `a_linear_value_comes_back_to_the_8_bits_the_curve_gives`.

## Verification

- `cargo test`: 663 passed, 2 ignored. `cargo clippy --all-targets -- -D
  warnings` and `cargo fmt --all --check` pass.
- Profile of the game's web build with the mipmaps' change: until the
  window, 25.1 s → 17.5 s on this container's CPU; `generate_mipmaps`
  10.1 s → 3.3 s.

## Still at the start (measured after the change)

`WorldTextures` 4.3 s (decoding, enhancing and the mipmaps of every ground
texture), `spawn_sky` 2.7 s, the bikes' models 2.7 s and the props' packs
2.5 s: every theme's props and every bike's textures are made as the game
starts, whichever circuit is to be shown first.

## 2026-11-07 — Loading stalls, stutters and crackling sound on the web

### User request

On the web the loading stops for moments, the game stutters and the sound
has many artefacts. Go ahead with loading on demand.

### Diagnosis

- **Sound.** Bevy plays through rodio and cpal, whose web backend keeps two
  buffers of 2048 samples (~46 ms each) queued, refilled from the page's one
  thread as each ends: every frame over ~90 ms left a gap, and its clock
  never caught up again (each buffer then started late, over the one
  before), so the sound crackled on after a single long frame.
- **Loading stalls.** In the tracks menu the engine prepared every circuit
  in the background, one after another (`queue_circuits`). On the web that
  "background" is the page's thread: each circuit stopped the page (and its
  sound) for seconds. Going past a circuit not yet built also built the
  whole of it at once.
- **Start.** Every theme's props were loaded as the game started (2.5 s
  here), whichever circuit is shown; `tiling_level` still went through
  `powf` for every pixel.

### Implementation

- `src/sound/output.rs` (new): the sound's own way out on the web, in place
  of Bevy's (whose `AudioPlugin` is disabled there, `src/lib.rs`). Each
  frame (`Last`) it writes what plays up to `Clock::ahead` (0.12 s, at most
  0.3 s) ahead of the speakers in chunks of 1024 samples, each scheduled at
  its time with Web Audio. A frame too long leaves one gap: the clock starts
  again from the speakers' time and keeps a little further ahead, nothing
  played over what played before. `Voices` mixes the synthesised effects
  and the songs, each volume ramping from chunk to chunk. Pure parts tested
  natively (`Clock`, `Voices`).
- `src/sound/mod.rs`, `music.rs`: on the web the mix and the songs go
  through it (`start_web_songs`, `WebSink`, which stops its song as its
  entity goes); elsewhere as before. `web-sys` gains the Web Audio features.
- `src/world/mod.rs`: on the web nothing is prepared in the background
  (`preparing_in_the_menus`); the circuit the tracks menu shows is built
  once the menu has rested on it 0.4 s (`Settling`, `settle_on_the_web`),
  with `CircuitLoading` set meanwhile.
- `src/world/prop_pack.rs`, `themes.rs`: `PropPacks` starts empty and loads
  a circuit's themes' packs the first time a circuit with them is built
  (`load_for`, `themes::packs_of`); `PropPack::load` takes the assets.
- `src/world/textures.rs`: `tiling_level` through the sRGB table.

### Verification

- `cargo test`: 667 passed, 2 ignored; `cargo clippy --all-targets -- -D
  warnings`, `cargo fmt --all --check` pass; `cargo clippy --target
  wasm32-unknown-unknown --lib` only the old `list_beside` warning.
- The game's web build with this engine, headless Chromium: until the
  window 17.5 s → 15.1 s (25.1 s on v0.0.21). One AudioContext; every chunk
  scheduled ahead of the speakers (none late), regular but for the
  start-up's multi-second frames, after which the clock restarted with no
  overlap. A race reached and driven (Bahía GP).
- Not measurable here: the stutters of a race on a real GPU (SwiftShader
  draws at ~1 FPS; the game's own code was ~1% of the page's thread).
